# Архитектура Проекта

Этот документ представляет собой высокоуровневый обзор архитектуры проекта, предназначенный для того, чтобы помочь разработчикам понять его структуру, ключевые компоненты и поток данных.

## 1. Обзор

Проект представляет собой сложную систему управления фермой Android-устройств для автоматизации действий в приложениях. Архитектура построена на многопроцессности и асинхронном выполнении задач, что позволяет эффективно распределять нагрузку и масштабировать операции.

Ключевые концепции архитектуры:
- **Service**: Абстракция над одним физическим устройством, содержащая собственную очередь задач.
- **Task**: Контейнер для одного конкретного скрипта автоматизации, который запускается в отдельном процессе.
- **GlobalServiceManager (GSM)**: Пул воркеров (процессов), который управляет выполнением `Service`'ов. Каждый воркер может обрабатывать один `Service` в один момент времени.
- **Dispatcher**: Высокоуровневый "мозг" системы, который получает бизнес-задачи (Заказы), находит свободные устройства (`Service`) и аккаунты, а затем распределяет `Task`'и по ним.

## 2. Структура Директорий и Ключевые Компоненты

### 2.1. `main.py`
Главная точка входа. Инициализирует `Core`, `Dispatcher`, `PanelManager` и запускает админ-панель в отдельном процессе.

### 2.2. `/core`
Сердце приложения. Здесь содержится центральная логика для оркестрации всей системы.

-   `core.py`: Класс `Core`. Отвечает за первоначальную загрузку конфигурации, обнаружение подключенных устройств (хабов и клиентов ADB) и создание `Service` для каждого из них. Предоставляет системные вызовы (`syscalls`) для `Dispatcher`'а, чтобы управлять `Service`'ами.
-   `dispatcher.py`: Класс `Dispatcher`. Реализует основную бизнес-логику. Он получает Заказы, находит свободные `Service` (устройства) и аккаунты, создает `Task`'и и загружает их в нужные `Service`, а затем отправляет эти `Service` на выполнение в `GSM`.
-   `service.py`: Класс `Service`. Представляет одно устройство. Имеет собственную внутреннюю очередь для `Task`'ов и хранит историю их выполнения.
-   `global_service_queue.py`: Класс `GlobalServiceManager` (GSM). Создает и управляет пулом дочерних процессов (воркеров), количество которых равно количеству ядер процессора. Каждый воркер забирает из общей очереди один `Service` и выполняет все `Task`'и внутри него.
-   `/tasks`:
    -   `task.py`: Класс `Task`. Обертка для функции-скрипта из папки `/scripts`. При запуске создает новый дочерний процесс для выполнения скрипта, что обеспечивает изоляцию и стабильность.
    -   `queue.py`: Простая реализация очереди на основе списка Python для внутреннего использования в `Service`.

### 2.3. `/db` и `/repository`
-   `/db`: Отвечает за низкоуровневое взаимодействие с базой данных (SQLite).
    -   `connector.py`: Управляет соединением.
    -   `controller.py`: Предоставляет базовые операции (add, delete, save).
    -   `/data`: Содержит модели данных SQLAlchemy.
-   `/repository`: Реализует паттерн "Репозиторий" (`repository.py`). Предоставляет более удобный и абстрактный API для работы с БД (CRUD, `findBy`, `readAll` и т.д.), используя `DatabaseController`.

### 2.4. `/services`
Высокоуровневые сервисы, реализующие конкретную бизнес-логику.

-   `/panel_manager`: Взаимодействует с внешней API-панелью для получения заказов (`Order`).
    -   `manager.py`: Основной менеджер, который использует `api_service` для запросов и `parser_service` для разбора ответов.
-   `/db_services`: Сервисы для управления конкретными сущностями в БД, например, `accounts_manager` и `order_manager`.
-   `/ai_manager`: Управляет взаимодействием с LLM.
-   `/ui_recognizer`: Сервис для анализа экрана устройства (XML-дампы, OCR, визуальный поиск).

### 2.5. `/scripts`
Конечная логика автоматизации. Содержит функции, которые непосредственно выполняют действия на устройстве через ADB.
-   Каждая функция-скрипт декорируется `@adbScript`, что указывает на ее предназначение.
-   Эти функции (`likePost`, `changeAccount` и т.д.) упаковываются в объекты `Task` для выполнения.

### 2.6. `/views`
Веб-интерфейс админ-панели на FastAPI. Запускается в отдельном процессе из `main.py`.

### 2.7. Прочие директории
-   `/meta`: Общие утилиты, исключения, схемы Pydantic, перечисления.
-   `/llm_data`: Данные для обучения и работы LLM.

## 3. Конфигурация
-   `core_configs.json`: Основной файл конфигурации для `Core` (например, таймауты, количество воркеров).
-   `.env`: Переменные окружения (ключи API, настройки БД).
-   `requirements.txt`: Зависимости Python.

## 4. Реальный Поток Данных

1.  **Инициализация**: `main.py` запускает `Core`, который находит все подключенные устройства и создает для каждого по объекту `Service`. Затем запускается `GlobalServiceManager` (GSM), который создает пул процессов-воркеров.
2.  **Получение Заказа**: `Dispatcher` в бесконечном цикле опрашивает `PanelManager` на предмет новых Заказов (например, "поставить 100 лайков на пост X").
3.  **Распределение**: Получив Заказ, `Dispatcher` ищет свободный `Service` (устройство) и свободный аккаунт на нем.
4.  **Создание Задачи**: `Dispatcher` создает объект `Task`, передавая в него ссылку на нужную функцию из `/scripts` (например, `likePost`) и необходимые аргументы (например, URL поста).
5.  **Загрузка Задачи в Устройство**: `Dispatcher` добавляет созданный `Task` во внутреннюю очередь выбранного `Service` с помощью системного вызова `core.addServiceTask()`.
6.  **Отправка на Выполнение**: `Dispatcher` отправляет `Service` (теперь с задачей внутри) на выполнение в `GSM` через `core.processService()`.
7.  **Выполнение Воркером**: Свободный воркер из пула `GSM` забирает `Service`. Он последовательно выполняет каждый `Task` из очереди `Service`, запуская его в отдельном дочернем процессе.
8.  **Сбор Результатов**: После выполнения всех `Task`'ов, `Service` помечается как завершенный. `Dispatcher` периодически проверяет историю выполненных `Service` через `core.serviceHistory()`, чтобы отслеживать прогресс Заказа.
9.  **Цикл**: `Dispatcher` продолжает шаги 3-8, пока весь объем Заказа (100 лайков) не будет выполнен, используя разные свободные `Service`.

## 5. Управление Аккаунтами и Устройствами

Система рассматривает устройства и аккаунты как два отдельных пула ресурсов. `Dispatcher` динамически связывает их для выполнения задач.

### 5.1. Фаза 1: Инвентаризация Аккаунтов
Этот процесс происходит один раз при запуске `Dispatcher.load()`:
1.  **Опрос Устройств**: `Dispatcher` перебирает каждый активный `Service` (устройство).
2.  **Запуск Скрипта**: На каждое устройство отправляется `Task` со скриптом `parseActiveAccounts`. Этот скрипт открывает в приложении меню смены аккаунта и считывает имена всех профилей, в которые уже выполнен вход.
3.  **Создание Карты**: Результаты собираются в словарь `_crspServiceAccount`. К концу этого процесса `Dispatcher` имеет полную карту вида `{"id_устройства": [список_аккаунтов]}`. Эта карта — основа для всей дальнейшей логики распределения.

### 5.2. Смена Аккаунта vs. Логин
Система спроектирована так, чтобы минимизировать ввод логина и пароля, так как это медленно и подозрительно для социальных сетей.
-   **Смена Аккаунта (`changeAccount`)**: Это основной режим работы. Когда `Dispatcher`'у нужно выполнить действие от имени аккаунта, он создает `Task` со скриптом `changeAccount`, который просто выбирает нужный профиль из списка уже залогиненных. Это быстро и имитирует нормальное поведение пользователя.
-   **Первичный Логин (`loginScript`)**: Этот режим используется редко, в основном для "подготовки" устройства, когда на него нужно добавить совершенно новый аккаунт. Это, как правило, полуавтоматическая операция, инициируемая администратором.

### 5.3. Логика Распределения Задач
Процесс выполняется в `Dispatcher._processOrder` для каждого Заказа:
1.  **Поиск Ресурсов**: `Dispatcher` в цикле ищет любую доступную комбинацию **свободного `Service`** (не находится в `_blockedServices`) и **свободного `ActiveAccount`** на нем (флаг `busy = False`).
2.  **Блокировка**: Как только пара найдена, ресурсы немедленно блокируются: `account.busy` становится `True`, а ID устройства добавляется в `_blockedServices`, чтобы другие потоки не могли их использовать.
3.  **Формирование Пакета Задач**: `Dispatcher` создает и загружает в `Service` как минимум две `Task`'и:
    1.  `Task(changeAccount, ...)` — для переключения на нужный аккаунт.
    2.  `Task(действие_заказа, ...)` — например, `likePost` или `followAccount` для выполнения самого задания.
4.  **Отправка на Выполнение**: Загруженный `Service` отправляется в `GSM`.
5.  **Освобождение Ресурсов**: После того как воркер `GSM` выполнит все задачи, `Dispatcher` получит отчет. Он найдет аккаунт и устройство, связанные с выполненной задачей, и снимет с них флаги блокировки, делая их снова доступными для следующего цикла.
6.  **Повторение**: Этот цикл "поиск -> блокировка -> выполнение -> освобождение" повторяется, пока весь объем Заказа не будет выполнен, эффективно используя всю мощь фермы.
